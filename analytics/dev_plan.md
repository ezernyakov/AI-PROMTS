## Требования к плану

### Важно: Проверка полноты ТЗ
Перед составлением плана проанализируй техническое задание на полноту и однозначность. Если есть неясности, противоречия или недостающая информация - ОСТАНОВИ составление плана и задай уточняющие вопросы. Не делай предположений о недокументированном поведении.

### Структура плана
План должен состоять из этапов с подэтапами:
- Этап (## Этап N: Название) - логически завершенная часть работы
- Подэтап (### N.M Название) - конкретное техническое действие

Используй только ## для этапов и ### для подэтапов. Не используй #### или другие уровни.

### Охват плана
План должен включать ТОЛЬКО разработку функционала:
- Создание/изменение классов, интерфейсов, методов
- Добавление полей, параметров, возвращаемых типов
- Интеграцию с SDK и другими компонентами
- Модификацию бизнес-логики

План НЕ должен включать:
- Тестирование (unit, integration тесты)
- Развертывание и деплой
- Написание документации
- Code review
- Настройку CI/CD

### Детализация подэтапов
Каждый подэтап должен содержать:
- Что именно создать/изменить (конкретный класс, интерфейс, метод)
- Где это находится (пакет, модуль)
- Какие поля/параметры добавить с указанием типов
- Какие аннотации применить
- Особенности реализации (обработка null, async, timeout и т.д.)

Используй маркированные списки (начиная с "-") для описания действий в подэтапе.

### Уровень детализации
Будь максимально конкретным:
- Указывай точные названия классов и методов
- Указывай типы полей и параметров (например, `List<String>`, `CompletableFuture<Void>`)
- Указывай конкретные аннотации (например, `@Nullable`, `@Service`)
- Описывай возвращаемые типы методов
- Упоминай особенности (nullable, optional, timeout значения)

НЕ используй абстрактные формулировки типа "реализовать бизнес-логику" или "добавить обработку ошибок" без конкретики.

### Формат вывода
- Используй markdown заголовки ## для этапов, ### для подэтапов
- Используй маркированные списки (-) для перечисления действий
- НЕ включай код - только описание того, что нужно сделать
- Начинай глаголами действия: "Создать", "Добавить", "Изменить", "Вызвать"
- Указывай конкретные имена классов в backticks: `ClassName`

### Пример структуры подэтапа

     ### 2.3 Реализация метода в SdkAdapterImpl

        - Добавить логирование начала операции с указанием ORPON ID
        - Вызвать вспомогательный метод для построения запроса
        - Вызвать метод SDK `cart.addProfile(bodyRequest, null)`
        - Использовать `execNative().async()` для асинхронного выполнения

        - В `thenApply` обработать MultiplatformIterator<Document> и залогировать успех
        - В `exceptionally` обработать ошибки и пробросить CompletionException
        - Вернуть `CompletableFuture<Void>` 


## Самопроверка и валидация плана

После составления плана проведи его оценку по следующим критериям. Каждый критерий оценивается от 0% до 100%.

### Критерии оценки

1. **Полнота покрытия ТЗ** (0-100%)
   - Все требования из технического задания отражены в плане
   - Нет пропущенных функций или компонентов
   - Учтены все интеграции и зависимости

2. **Детализация реализации** (0-100%)
   - Указаны конкретные классы, интерфейсы и методы
   - Определены типы параметров и возвращаемых значений
   - Перечислены необходимые аннотации
   - Описаны особенности реализации (null-safety, async, timeouts)

3. **Структурная организация** (0-100%)
   - Логичное разбиение на этапы и подэтапы
   - Правильная иерархия заголовков (## для этапов, ### для подэтапов)
   - Каждый подэтап описывает одно конкретное техническое действие
   - Нет дублирования между подэтапами

4. **Техническая корректность** (0-100%)
   - Соответствие архитектуре системы из технической документации
   - Правильное использование SDK согласно документации и коду SDK
   - Соблюдение best practices Spring Boot
   - Корректные зависимости между компонентами

5. **Последовательность выполнения** (0-100%)
   - Логичный порядок реализации (от базовых компонентов к сложным)
   - Учтены зависимости между этапами
   - Нет циклических зависимостей
   - Возможность инкрементальной реализации

### Формат оценки

Представь оценку в виде таблицы:

| Критерий | Оценка | Комментарий |
|----------|---------|-------------|
| Полнота покрытия ТЗ | X% | Краткое пояснение |
| Детализация реализации | X% | Краткое пояснение |
| Структурная организация | X% | Краткое пояснение |
| Техническая корректность | X% | Краткое пояснение |
| Последовательность выполнения | X% | Краткое пояснение |

### Итеративное улучшение

Если хотя бы один критерий имеет оценку ниже 95%:

1. Выяви конкретные проблемы для каждого критерия < 95%
2. Внеси исправления в план разработки
3. Проведи оценку обновленного плана заново
4. Повторяй шаги 1-3 до достижения 95%+ по всем критериям

После каждой итерации указывай:
- Какие изменения внесены
- Как они улучшили план
- Новые оценки по критериям

ВАЖНО: Итоговый план должен иметь оценку не ниже 95% по каждому из пяти критериев.
