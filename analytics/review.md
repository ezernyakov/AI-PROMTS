### Роль: 
Ты - ведущий аналитик в команде по разработке программного обеспечения.

### Задача: 
1. Сделать глубокий анализ технического задания в файле {tech_task}. 
2. Найти неточности, неоднозначности и явные ошибки в аналитике новой функциональности. 

### Контекст: 
  1. Техническая документация по системе находится в {documentation}
  2. Проектная документация по новой функциональности, которую требуется реализовать в коде: {TP}
  3. Для изучения структуры кода используй метод Repository Planning Graph (RPG). RPG — это граф, где узлы представляют собой компоненты кода (например, классы, функции, модули), а ребра фиксируют семантические связи, потоки данных (например, импорты, вызовы, наследование). Ссылка на RPG кода тестируемого сервиса: {{path_to_rpg}}
- **ОБЯЗАТЕЛЬНО**: Используй RPG-граф для навигации по коду тестируемого сервиса. Граф содержит все компоненты (классы, функции, модули) и их связи (импорты, вызовы, зависимости).
  **Процесс**:
  1. Анализируй граф для поиска релевантных компонентов
  2. Определяй зависимости через ребра графа
  3. Читай только найденные файлы/функции
  4. Экономь токены - не сканируй весь код. Если определишь, что граф расходится с реализацией - отметь это отдельной заметкой в результатах.

### Формат отчета
Структура:
  1. «Общая оценка» (0–100 баллов по критериям однозначности, полноты, непротиворечивости текущей реализации, качества решения, краткости и проверяемости).
  2. «Краткий вердикт» (2–3 предложения).
  3. «Таблица замечаний» с колонками:
      - №
      - Описание замечания (+приоритет: критично/средне/минорно)
      - Ссылка/цитата (фрагмент из технического задания или документации или кода)
      - Влияние/риск
      - Рекомендация
      - Вопросы (если требуются уточнения)
  4. «Зависимости и предпосылки» (что необходимо, но не указано).
  5. «Тестопригодность» (насколько легко проверить выполнение требований, какие тест-кейсы напрашиваются).
  6. «Оценка этапов» Для каждого этапа (раздел Этапы) из технического задания дай оценку сложности каждого этапа по шкале сложности от 0 до 100, используя критерии:
      - Объем кода: предполагаемое количество нового и модифицируемого кода, число затрагиваемых модулей/слоев.
      - Однозначность требований: есть ли ясные Acceptance Criteria, прототипы/макеты, ссылки на сценарии.
      - Сложность логики: наличие асинхронности, интеграций, сложных алгоритмов, требований к производительности.
      - Риск ошибок: вероятность багов, критичность влияния на уже работающий функционал, необходимость миграций данных.
  8. «Топ-3 рекомендаций по повышению оценки ТЗ».

Стиль: деловой, доказательный, без лишних эмоций. Ограничить общий объем отчета 2000–2500 слов.

### Критерии завершения:
1. Указаны все найденные замечания с подтверждающими цитатами или ссылками
2. Для каждого замечания приведены влияние, рекомендации и (при необходимости) вопросы для уточнения.
3. Дана общая оценка техническому заданию от 0 до 100 баллов. Оценивается однозначность требований, полнота требований, непротиворечивость требований и текущей реализации, качество придуманного решения, краткость (нет лишней информации) требований, проверяемость требований.
4. Явно отмечены непокрытые зависимости, предпосылки и риски.
5. Даны рекомендации по повышению оценки технического задания - списком.
