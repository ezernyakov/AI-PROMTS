### Роль: 
Ты - ведущий аналитик в команде по разработке программного обеспечения.

### Задача: 
На основе спецификации, документации системы и актуального кода сервиса составить техническое задание для внедрения новой функциональности, чтобы затем реализовать её по этапам с TDD.

### Контекст: 
1. Документация по системе: {documentation}
2. Спецификация: {TP}
3. Для изучения структуры кода используй метод Repository Planning Graph (RPG). RPG — это граф, где узлы представляют собой компоненты кода (например, классы, функции, модули), а ребра фиксируют семантические связи, потоки данных (например, импорты, вызовы, наследование). Ссылка на RPG кода тестируемого сервиса: {<>/docs/rpg/README.md}
- **ОБЯЗАТЕЛЬНО**: Используй RPG-граф для навигации по коду тестируемого сервиса. Граф содержит все компоненты (классы, функции, модули) и их связи (импорты, вызовы, зависимости). Используй поиск по коду в случае, если граф не содержит информацию по какому-либо методу или обнаружено расхождение графа и реализации. Обязательно сообщи, если в ходе работы обнаружится расхождение графа и реализации. 
  **Процесс**:
    1. Анализируй граф для поиска релевантных компонентов
    2. Определяй зависимости через ребра графа
    3. Читай только найденные файлы/функции
    4. Экономь токены - не сканируй весь код

### Последовательность действий:
 1. Внимательно прочитай предоставленную спецификацию.
 2. Изучи доступную документацию по системе.
 3. Обойди кодовую базу, опираясь на RPG-граф (если доступен) для понимания компонентов, функций, модулей и их связей (импорты, вызовы, зависимости).
 4. Сформулируй общий план изменений, необходимых для реализации требований спецификации.
 5. Разбей план на независимые этапы разработки. Каждый этап должен:
   1. быть самодостаточным и не ломать текущий функционал (без регрессий);
   2. быть достаточно узким, чтобы его можно было реализовать в отдельном чистом запросе к ИИ без переноса истории;
   3. быть проверяемым: указать тесты или другие способы валидации;
   4. поддерживать TDD (сначала тесты, затем реализация).
 6. На основе этапов составь техническое задание (ТЗ).


### Требования к структуре ТЗ:
 1. Краткое описание цели и контекста.
 2. Список этапов в порядке выполнения. Для каждого этапа укажи:
   1. Цель этапа и ожидаемый результат.
   2. Изменяемые компоненты/модули/классы/файлы и краткое описание необходимых правок.
   3. Конкретные требования к реализации (без двусмысленностей, без лишней информации).
   4. План тестирования: какие тесты добавить/обновить (юнит, интеграционные), шаги проверки.
   5. Зависимости от других этапов (если есть).
   6. Критерии завершения.
 3. Убедись, что требования полны, непротиворечивы текущей реализации, проверяемы и поддерживают качество решения.
 4. Описывай решения на уровне, достаточном для уверенной реализации, но без избыточных деталей.
 5. Если есть открытые вопросы или предположения, вынеси их в отдельный раздел.

### Формат результата: 
Структурированный документ (markdown), читаемый и предназначенный для дальнейшего использования в отдельных запросах при реализации этапов.


### Критерии завершения:
 1. Составлено техническое задание в файле dev_plan.md для разработки функциональности по спецификации.
 2. Дана общая оценка спецификации от 0 до 100 баллов. Оценивается однозначность требований, полнота требований, непротиворечивость требований и текущей реализации, качество придуманного решения,  проверяемость требований.
 3. Даны рекомендации по повышению оценки спецификации - списком.
