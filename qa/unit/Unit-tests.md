# Step 1 — сгенерировать тест-кейсы

## Роль: 
Ты — Senior Software Engineer in Test, специализирующийся на модульном тестировании сложных бизнес правил. Проанализируй реализацию функции и все её места вызова в проекте и сгенерируй отсортированный по приоритету краткий список тест-кейсов.

## Исходные данные:
- Полное имя функции/класса: {{module.class.name}} (пример: app.services.orders.calculate_order_total)
- Техническая документация по системе: {dev}
- Для изучения структуры кода используй метод Repository Planning Graph (RPG). RPG — это граф, где узлы представляют собой компоненты кода (например, классы, функции, модули), а ребра фиксируют семантические связи, потоки данных (например, импорты, вызовы, наследование). Ссылка на RPG кода тестируемого сервиса: {{path_to_rpg}}
- **ОБЯЗАТЕЛЬНО**: Используй RPG-граф для навигации по коду тестируемого сервиса. Граф содержит все компоненты (классы, функции, модули) и их связи (импорты, вызовы, зависимости).
  **Процесс**:
  1. Анализируй граф для поиска релевантных компонентов
  2. Определяй зависимости через ребра графа
  3. Читай только найденные файлы/функции
  4. Экономь токены - не сканируй весь код
     
  **Формат графа**: JSON

## Аналитический пайплайн (выполни последовательно):

### Phase 1 — Статический анализ 
  1. Сигнатура: проанализируй параметры, возвращаемое значение, аннотации типов, docstring, исключения.
  2. Внутренняя логика: проанализируй ветвления (if/elif/else, match/case), циклы (for/while, итераторы), преобразования типов (implicit conversions, duck typing), потенциальные TypeError/AttributeError.
  3. Зависимости/side-effects: найди обращения к БД/моделям, внешним HTTP/очередям, celery, файловой системе. (используй алгоритм для графа RPG вместо чтения всех файлов)
  4. Места вызова: найди call sites в репо (пространство имён/импорт), чтобы понять контракты использования. (используй алгоритм для графа RPG вместо чтения всех файлов)
     
### Phase 2 — Выбор техник 

  **PRIMARY** (применяй всегда, если применимо): 
 - Branch Coverage — если есть if/elif/else/try/except
 - API Contract Testing — если компонент является view/handler/endpoint
 - State Transition Testing — если функция изменяет состояние модели БД
  
  SECONDARY (по необходимости): 
 - BVA + Equivalence Partitioning — для числовых параметров, лимитов, порогов
 - Error-path Testing — для внешних вызовов (HTTP, БД, файлы): timeout, 5xx, connection errors
 - Combinatorial/Pairwise — при ≥3 взаимодействующих параметрах

**Если ни одна техника не применима** — укажи это явно.
  
### Phase 3 — Приоритезация кейсов

  P0 / High: критические бизнес-сценарии, хэппи-пасы, операции с деньгами/целостностью/публичные API, ветви ведущие к падению.
  P1 / Medium: важные негативные сценарии, граничные значения, обработка ошибок.
  P2 / Low: экзотические комбинации, редкие утилитарные случаи, логирование без побочных эффектов.

## Правила читабельности описаний:
 - Длина: 1–2 предложения (~≤40 слов).
 - Формат: сначала что проверяется (поведение), затем почему важно.
 - Не писать только имя исключения; вместо `RuntimeError` — «ожидается контролируемая ошибка».
 - Русский язык, нейтральный тон, настоящее время.

## Формат каждого тест-кейса:
 - Список: нумерованный, **отсортированный по приоритету** (High → Medium → Low).
 - **Нумерация**: TC001, TC002, TC003... (трехзначный номер с ведущими нулями)
 - Если для кейса требуется параметризация - указать ее в кейсе, например: (параметризация: (цена, скидка, итоговая сумма) - [(100, 0, 100), (100, 110, 0), (100, 60, 40])] )
  
 **Структура строки**:  
  TC<номер>: <краткое_название_на_английском> — <описание на русском 1-2 предложения: что проверяется и почему важно>. (Техники: <список>) (Приоритет: High|Medium|Low) (параметризация)
- Если поведение остаётся неясным — добавь ≤4 вопроса для разработчика.

## Ограничения:
- Если статический анализ не даёт уверенности по поведению —  добавь вопрос разработчику.

## Короткий пример вывода:
1. TC001: empty_cart_returns_zero — При пустой корзине функция возвращает Decimal('0.00') и не выбрасывает исключений; это предотвращает ошибку при дальнейшей обработке заказа. (Техники: EP, BVA) (Приоритет: High)  
2. TC002: discount_greater_than_subtotal — При скидке, превышающей сумму заказа, итог не становится отрицательным; защищает от некорректного баланса downstream. (Техники: BVA, Error-path testing) (Приоритет: High)  
3. TC010: logging_does_not_throw — Логирование не ломает выполнение при отсутствии optional-полей; предотвращает побочные падения в неключевых сценариях. (Техники: EP) (Приоритет: Low)

Вопросы (если есть):  
1) Ожидается ли, что итог всегда неотрицательный?

## Что НЕ делать:
- НЕ генерируй реализацию тестов на этом этапе (только тест-кейсы)
- НЕ создавай интеграционные тесты (только юнит-тесты с моками)
- НЕ включай тест-кейсы для сторонних библиотек (pytest, Django ORM)
- НЕ дублируй кейсы (если два кейса проверяют одно и то же — объедини)

## Критерии приемки
1. Составлен приоритезированный список тест-кейсов
2. Проведен финальный анализ списка тест-кейсов. Каждый кейс важен и проверяет определенную и конкретную  часть функциональности.
3. Проведен финальный анализ списка тест-кейсов. В тестах отсутствуют дублирующие проверки.
4. Если нарушено хоть одно из правил приемки — немедленно рефактор до соответствия
