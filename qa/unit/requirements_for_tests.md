## Требования:
1. Выбери фреймворк для тестирования (например, pytest). Предложи и обоснуй выбор.
2. Выбери фреймворк для моков/стабов. Предложи и обоснуй выбор.
3. Дополнительные утилиты для тестирования, если необходимы. (Например, django-pytest для Django-сервисов)
4. Опиши требования к структуре и качеству тестов: 
   - Структура (Arrange-Act-Assert)
   - Читаемость имен тестов
   - Изоляция тестов
  
5. Зона ответственности unit‑тестов:
   - Что считается unit‑тестом: чистая логика модуля, изоляция внешних эффектов через моки/фейки.
   - Что не является unit‑тестом: сеть/БД/файловая система/время/потоки — выносить в фейки/контракты/интеграционные сьюты.
   - Границы: модульный контракт (вход/выход/исключения/инварианты), отсутствие зависимостей от порядка выполнения.
  
6. Политика моков/стабов/фейков:
  - Мокать только внешние границы/нестабильные зависимости.
  - Запрет: моки внутренних деталей реализации, snapshot‑тесты без чётких контрактов.
  - Правила: чёткие ожидания (verify), минимально необходимая конфигурация, негативные кейсы на ошибки зависимостей.

7. Стандарты дизайна тестов:
  - Структура: Arrange‑Act‑Assert (или Given‑When‑Then) — явно отделять блоки.
  - Техники:
     - Equivalence classes, Boundary values, Table‑driven tests, Property‑based для инвариантов, Mutants‑driven refinement (мутационное тестирование для выявления слабых ассертов).
  - Анти‑паттерны: тесты‑паразиты, дублирование фикстур, магические константы — выносить в именованные фабрики/константы.

8. Фикстуры и тест‑данные:
 - Фабрики/генераторы вместо хардкода; обязательные сиды для детерминизма.
 - Очистка состояния: teardown/fixtures/autouse cleanup, запрет глобальных синглтонов без сброса.
