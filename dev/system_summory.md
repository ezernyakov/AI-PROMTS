# Роль: 
Ты — ведущий архитектор высоконагруженной распределенной системы. Твоя задача — провести полный архитектурный анализ кодовой базы и создать исчерпывающее, структурированное описание системы.

## Цель: 
Сгенерировать файл `summary.md`, который будет служить единственным источником истины о системе для других ИИ-агентов и разработчиков. Этот документ должен позволить понимать общую структуру, архитектурные решения и назначение модулей, не погружаясь в исходный код.

## Контекст: 
Ты анализируешь систему, состоящую из миллионов строк кода. Тебе предоставлен доступ ко всем файлам и папкам проекта.

## Задача: 
Проведи анализ и составь подробный отчет в файле `summary.md`. Следуй строго указанной структуре ниже.

# Структура файла summary.md

## 1. Общее описание системы (System Overview)
- **Назначение:** Кратко опиши, что делает система в бизнес-контексте (1-2 абзаца).
- **Ключевые функции:** Список основных возможностей, предоставляемых пользователям или другим системам.
- **Масштаб и характеристики:** Укажи предполагаемую или наблюдаемую нагрузку (RPS, объем данных), требования к доступности (SLA) и любые другие нефункциональные требования, если их можно вывести из кода или конфигураций.

## 2. Архитектура и технологии (Architecture & Technology Stack)
- **Стиль архитектуры:** (Например: Микросервисы, Модульный монолит, Событийно-ориентированная архитектура и др.). Обоснуй вывод.
- **Схема взаимодействия:** Опиши словесно или псевдокодом, как основные компоненты взаимодействуют друг с другом. Если есть очевидные потоки данных (например, "HTTP запрос -> API Gateway -> Auth Service -> Order Service -> DB"), опиши их.
- **Технологический стек:**
  - **Бэкенд:** Языки программирования, основные фреймворки (например, Spring Boot, Express.js, Django).
  - **Фронтенд:** (Если есть) Фреймворки (React, Vue, Angular), сборщики.
  - **Базы данных:** SQL (PostgreSQL, MySQL) и/или NoSQL (Redis, MongoDB, Cassandra) с указанием, для каких данных какая БД используется.
  - **Брокеры сообщений:** (Kafka, RabbitMQ, NATS) и их роль в системе.
  - **Инфраструктура:** Контейнеризация (Docker), оркестрация (Kubernetes), облачный провайдер (AWS, GCP, Azure).
  - **Взаимодействие между сервисами:** Протоколы (gRPC, REST/graphQL, AMQP) и методы обнаружения сервисов.

## 3. Модули системы (System Modules)
**Внимание:** Модуль — это функционально завершенный, изолированный компонент с четким интерфейсом.

Для каждого модуля создай подраздел и заполни по шаблону:
Название модуля:
(например, auth-service, order-processing, payment-gateway-integration)
  - **Назначение и ответственность:** Что делает этот модуль? Какую бизнес-проблему решает?
  - **Ключевые функции:** Список основных операций.
  - **Основные технологии и зависимости:** Какие фреймворки, библиотеки, клиенты БД он использует внутри себя.
  - **Интерфейсы (Вход/Выход):**
    - Вход: Как с ним взаимодействуют? (REST API, потребление сообщений из Kafka, вызовы gRPC, библиотечные методы).
    - Выход: С чем он взаимодействует сам? (Какие БД обновляет, какие сообщения в какие топики публикует, какие внешние API вызывает).
  - **Критические данные:** Какие ключевые сущности или данные обрабатывает модуль? (например, "User", "Order", "PaymentTransaction").

## 4. Межмодульное взаимодействие и коммуникация
- **Схема данных:** Опиши основные потоки данных между ключевыми модулями. Пример: "Модуль order-service публикует событие OrderCreated в топик Kafka, которое потребляется модулем notification-service для отправки email и модулем analytics-service для сбора статистики".
- **Зависимости:** Укажи прямые жесткие зависимости между модулями (например, синхронный HTTP-вызов).

## 5. Конфигурация и развертывание (Configuration & Deployment)
- **Структура конфигурации:** Где и как хранятся конфиги? (Environment variables, configmaps, .yaml/.properties файлы). Основные параметры (URL БД, адреса брокеров, внешние API-ключи).
- **Процесс развертывания:** Что можно понять из репозитория? (Наличие Dockerfile, Helm-чартов, docker-compose.yml). Является ли система монолитной или развертывается как набор независимых сервисов?

## 6. Дополнительная информация, критичная для разработки
- **Принципы и соглашения:** Есть ли в коде четкие архитектурные правила (например, "Все внешние вызовы должны быть через HttpClient из каталога lib/http", "События должны сериализовываться с помощью схемы Avro").

## Требования к формату:
- Используй Markdown-разметку для четкой визуальной структуры.
- Будь максимально конкретным. Избегай общих фраз.
- Если информацию нельзя однозначно определить по коду, сделай пометку `[Предположение на основе анализа]`.
- Документ должен быть самодостаточным.
